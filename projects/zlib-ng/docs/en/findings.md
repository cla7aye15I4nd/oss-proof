# Findings: issues found in zlib-ng

The work found twenty-one issues in the zlib-ng `develop` branch at the verified commit. Each is a defect of zlib-ng
itself, is reached through functions that `zlib.h` documents, and is shown by a run of the real C (or, where a
sanitizer cannot see it, by the letter of ISO C17 on a traced run). Patches 0003, 0004, 0006, 0007, 0008, 0009,
0010, 0011, 0012, 0013, 0014, 0015, 0016, 0017, 0018, 0019, 0020, 0021 and 0022 fix the first twenty: one patch each, except patch 0014, which
fixes the two issues of a failed `gzwrite` (one stale pointer causes both). The last issue (`deflateReset` with a static
block open) gives a wrong result without a memory error and is not patched.

The evidence column labels how each issue was shown. **Public API**: a program that makes only documented calls
(its failures and devices come from ordinary descriptors), and the defect is seen on the run: a sanitizer report or a
wrong result. **Letter of the standard**: the calls are documented ones too, but no sanitizer reports the undefined
behaviour and nothing misbehaves; the evidence is the wording of ISO C17 applied to a traced run. **White-box** would
be a test that sets the library's internal state itself; no issue here rests on one. A report of AddressSanitizer's
pointer-pair check is a report of behaviour that is undefined by the letter of the standard and that misbehaves on no
flat-memory target.

| Two streams sharing one `gz_header` overrun its extra buffer | `inflate` (state `EXTRA`) places the extra field at `len = head->extra_len - state->length` and bounds the copy with `len < extra_max` and `len + copy > extra_max`, all in 32-bit `unsigned`. When two streams share the header, the other stream's `EXLEN` can store a smaller `extra_len`; `len` then wraps to nearly 2^32, and with `extra_max` near 2^32 `len + copy` also wraps, so `memcpy` writes past the end of the buffer. | `inflateInit2(a, 31)`, `inflateGetHeader(a, &g)` with `g.extra_max = 0xffffffff`, `inflate(a)` up to the extra length, `inflateCopy(b, a)` (or a second `inflateInit2(b, 31)`, `inflateGetHeader(b, &g)`), `inflate(a)` reading extra length 100, `inflate(b)` reading extra length 10, `inflate(a)` with 100 bytes of the extra field | **Public API**: AddressSanitizer heap-buffer-overflow, `inflate.c:625` (write of 100 bytes, 11 past the buffer) | Patch 0011 | not submitted |

| `deflate` divides by zero after `deflateTune` with a negative `max_lazy` | `deflateTune` stores `max_lazy` as it is. | A failed `gzwrite` leaves the stream pointing into the caller's buffer; a write after `gzclearerr` subtracts unrelated pointers | A `gzwrite` of at least the buffer size takes the direct path of `gz_write`, which points `strm.next_in` at the caller's buffer. | gz position overflow, writing | The writers add the length of each write to the signed 64-bit position `x.pos` without a bound, before they write: after `2^63` bytes in all, signed overflow in `gz_write` (also `gzputc` and `gzprintf`). | A failed write of a seek's zeros moves the writer's position past the seek | A forward `gzseek` on a writer only records the skip; the next write calls `gz_zero`, which writes the zeros in batches. | `gzgets` reads past the end of file while a seek is pending | A pending seek on a reader (`skip != 0`) is done by `gz_skip` before the next read. When the input ends first, `gz_skip` stops with the skip still pending (end of file set, no input or output buffered). `gzread`, `gzfread` and the `gzgetc` function (through `gz_read`) then stop as well, at the end-of-file test. `gzgets` instead calls `gz_fetch`, which in copy mode (input that is not gzip) reads again although the end of file was set. Only documented calls; the condition outside the program is that the file grows between two calls | **Public API**: UndefinedBehaviorSanitizer, `gzlib.c:496`; the condition outside the program is that the file grows between two calls | Patch 0021 | not submitted |

After `deflateReset` with the block still open, the next stream continues that block: its symbols follow the new zlib header without a block header. `inflate` rejects the output. A wrong result, with no memory error. | `deflateInit2(strm, 1, Z_DEFLATED, 15, 8, Z_FIXED)`, `deflate(strm, Z_NO_FLUSH)` over 3000 bytes, `deflateReset`, `deflate(strm, Z_FINISH)` over 1000 bytes, then `inflate` of that output | **Public API**: a run of the real C: 27 bytes of output, which `inflate` rejects with `Z_DATA_ERROR` ("invalid stored block lengths") | not patched | not submitted |

Issues found in the earlier 2.3.3 release (`gzbuffer` size overflow, `crc32_combine*` not returning for a negative
length, `adler32` with `NULL` and length 1) are fixed on the `develop` branch; their reproductions remain as
regression tests.

The runs were made on an LP64 build of the verified sources in the verified configuration (see the
[overview](index.html)), with every patch except the one that fixes the issue, not on the x86_64 Linux target
itself. With every patch, each patched issue runs without a sanitizer report and returns (the gz position overflow was shown on a host whose
`/dev/zero` does not behave as Linux's, with its `lseek` answered as Linux answers it).

A sanitizer report or a run of the real C is evidence about that run. It is not a proof. The safety theorems are
about the patched source.
