## F1. 结构相等强于逐项一致

历史严重程度：低，属于完备性和命题设计的问题。`Tbl` 存放一个数组。在末尾之后写入一个默认值会使数组变长，尽管所有可观察的表项都没有变。因此，不可能有一条外延性定理把表项全部相同的表都认作同一张表。

审查编译了下面这些反例：

```lean
theorem neq : upd (Tbl.empty : Tbl (Option Nat)) 3 none ≠ Tbl.empty := by
  intro h
  have := congrArg (fun t => t.arr.size) h
  simp [upd, Tbl.set, Tbl.empty] at this

example : ¬ ∀ (t : Tbl (Option Nat)) k, t k = none → upd t k none = t := by
  intro H
  exact neq (H Tbl.empty 3 (by simp))

example : ¬ (∀ (a b : Tbl (Option Nat)), (∀ k, a k = b k) → a = b) := by
  intro H
  have := H (upd Tbl.empty 3 none) Tbl.empty
    (by intro k; by_cases k = 3 <;> simp_all [upd_apply])
  exact neq this
```

`upd Tbl.empty 3 none` 的数组大小是四。分配一个字节再释放之后，字节表里留下一个 `none` 槽位。所以，“分配再释放之后堆完全复原”与“存活对象和表项复原”不是同一个命题。

以表相等为前置条件，也可能比逐项的条件更窄。审查在 `Schema.lean` 之外的搜索没有发现这样的假设；检查过的命题锁中的表相等都出现在结论里。这次搜索只是有限范围内的证据，不能一般地保证定义域不是空的。一个不成立的复原目标是规格问题，需要另行审查；不得为了完成证明而悄悄削弱它。[可信基础](../trusted-base.md)解释了这两种相等的区别。

## F2. 大的块编号导致按比例的数组分配

历史严重程度：低，属于求值开销。`Tbl.set` 的扩展分支一直填充到所选的下标。在编译的例子中，对空表设置下标 3,000,000 产生了 3,000,001 个槽位。从空堆出发，分配编号每次增加一，表的大小不超过分配次数。而手工构造的巨大 `nextBlk`，在求值或内核化简时可能需要一个巨大的数组。这是测试和见证在资源上的隐患，不是错误的数学结果。审查过的不变量没有给 `nextBlk` 设上界。

## F3. 注释仍在描述函数表的闭包

历史严重程度：低，属于文档问题。旧的 `Space.lean` 文件头把 `upd` 描述为更新一个函数。deflate、inflate 和回调式 inflate 的驱动程序注释描述了闭包的压紧和扁平化。它们的重建步骤保持每一个表项，但可能改变结构相等。驱动程序不比较表，所以没有发现不正确的观察结果。这些是审查当时关于注释的发现；之后的文字须另行评估。

## F4. 类法则只约束对存活引用的修改

历史分类：提示性；是否需要这条法则尚未确认。`Space.modify_eq` 假设 `get h r = some a`。对已死引用的修改，它什么也没有说。生成的实例安全地处理已死的引用，审查过的原语先检查存活性。之后若有不做检查的调用者，仅凭这条类法则推不出对已死引用的行为。提议增加的法则是 `get h r = none → modify h r f = h`；检查过的调用者并不需要它。

## F5. 锁覆盖了定义；缺少针对性的反向自测

历史严重程度：低，属于检查的覆盖面。检查过的可信锁覆盖 `C.Tbl`、它的数组字段、get、set、modify、empty、强制转换和默认实例、`C.upd`、`C.Space`、`Space.modify`，以及生成的实例及其辅助定义。类型加取值的指纹包含 `Space.mk` 中的 `modify_eq` 字段。辅助定理经过内核检查和公理审计，没有做语义上的锁定。

已有的“触碰运行时”和“削弱运行时”两个取巧用例检验了一般的机制。审查没有发现针对性的取巧用例，例如让 `Tbl.get` 忽略它的数组，或让修改复活一个已死的块。没有实际运行对这些变异的检测，因此这一项具体覆盖尚未确认。这项发现并不是削弱审计的许可。

## F6. 释放后的槽位仍然占着模型的表存储

历史分类：提示性。块编号从不重用。释放是把表项换成 `none`，不是缩短数组。因此每张用过的表都保留着直到它分配过的最大块编号的槽位。旧的闭包表示有同样的增长阶和更差的常数。这是“编号从不重用”这一模型的性质，与已证明的、存活 zlib 对象的所有权是两回事。

## 给以后的审查的经验

把对象层面的帧性质和所有权结论，与表示方式上的存储相等分开。审查关于任意堆的前置条件时，要像审查从空堆出发的运行一样仔细。原地修改之前要求检查存活性，并保持类法则与它的各个生成实例之间的区别。编译过的例子和源码搜索有助于检验这些边界；它们并不确立整个运行时对 C 的忠实性，也不能代替独立的批准。
