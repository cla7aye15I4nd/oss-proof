# 可信运行时审查记录

> **带日期的记录。** 这是一次对运行时的源码审查，写于 2026-11-06，针对当时读到的定义和文档。它不是现有缺陷的列表，也不是对运行时的批准。下表给出每项发现在 2026-11-14 的状态。模型的限制现在怎样表述，见[可信基础](../trusted-base.md)；当前的工作见[进度页](../progress.md)。

## 范围与证据

审查读了 `ZlibF/Runtime/` 的模块 `Space`、`Monad`、`Ptr`、`Alloc`、`Tables` 和 `Schema`，结构定义的生成器，运行时结构定义的文档，安全文档和翻译规则。它把这些与固定的 `zlib.h`、`deflate.h`、`inflate.h`、`inftrees.h`、`gzguts.h`、`zutil.h`、`zconf.h`、`deflate.c`、`inflate.c`、`trees.c` 和 `uncompr.c` 相比较。第一遍之后，又以挑错的方式重读了一遍。没有做任何构建或差分运行。下文的“已确认”是指有这些定义和对源码的解读作依据，不是指编译通过的证明或 sanitizer 复现。审查没有改动任何源码。

严重程度衡量的是这样一个结论所受的风险：模型运行成功，就排除了 C 的未定义行为。“高”表示它能让一个实质上错误的安全论证成立；“中”表示还需要另有一处翻译或定理错误才出问题，或者它给出的语义与 C 不同；“低”表示只涉及完备性或文档。这些评级是历史记录，不是对上游漏洞的评级。

审查发现，故障经由 monad 传播，循环规则不会掩盖燃料耗尽。它关心的是表示的边界、缺失的初始化历史、结构定义中的常量，以及文档中言过其实之处。

## 发现 R1–R13

### R1. 新分配的指针字段被建模为 NULL，而不是不确定的指针

历史严重程度：对一般性的结论为高，对审查过的 zlib 路径为中。`Schema.lean` 的垃圾构造子使用默认指针；`Space.lean` 把这个默认值定义为 NULL；`Tables.lean` 分配这样的记录。于是，分配一条记录、读取一个未写入的指针，再把它与 NULL 比较或传给 `freeB`，都可能成功。对整数垃圾值的量化没有覆盖不确定的指针。

审查用下面的 C 例子揭示这个缺口：

```c
z_stream *s = malloc(sizeof *s);
if (s) { free(s->next_in); free(s); }
```

审查过的 inflate 和 deflate 初始化路径在分配之后立即把各自的状态清零。其他记录，尤其是 `gz_state`，需要另行检查。建议的补救办法是给指针字段加初始化标记，或引入显式的“未初始化指针”值。实质的证明义务是时序上的：每个指针字段都必须先写入、后读取。旧的安全文档和翻译文档声称这里会出故障，而结构定义的文档说的是 NULL；这一矛盾也是 R1 的一部分。

### R2. NULL 指针运算是一项语义上的决定

历史严重程度：低。`Ptr.add` 和 `Ptr.add_null_zero` 接受 `NULL + 0`。审查把这看作模型有意设置的例外，不是新发现的 zlib 缺陷。它当时标注的日期并不确立这在 C23 中有定义；见[当前对操作与语言的对照](../spec/safety.md#null-pointers-and-pointer-differences)。它还记录了 `Ptr.diff null null` 会出故障。所支持的 C 方言和 NULL 运算的例外都必须在可信基础中写明；证明不得把模型的一项决定悄悄变成关于所有 C 构建的结论。

### R3. 结构定义中的一个名字代表两个不同的 `COPY` 常量

历史严重程度：若被使用则为高，按审查到的可达范围为中。`Schema.COPY` 是 inflate 的模式值 16195，而 `gzguts.h` 把 `COPY` 定义为 1，用于 `state->how`。生成器跳过与枚举常量同名的宏。因此，使用这个共用名字的 gz 翻译验证的就可能是错误的状态机。`GZIP` 也有类似的名字冲突，不过它的数值与 gz 的用法一致。建议的补救办法：使用不同的名字，或把常量限定在各自的翻译单元内。

### R4. 枚举常量被赋予无符号类型

历史严重程度：中。枚举常量的值与 C 一致，但结构定义给 `HEAD`、`CODES` 这样的常量以类型 `UInt32`。在审查的目标平台上，C 的枚举常量类型是 `int`。例如，把 `int x = -1` 与 `HEAD` 相比较，如果常量迫使比较按无符号进行，结果就不同。字段的存储类型正确，并不能纠正常量表达式的类型。提出的补救办法是把有符号常量与转换成枚举存储类型的操作分开。

### R5. 固定的数组长度和静态内容需要不变量

历史严重程度：中。记录的字段是 Lean 数组，C 中的长度只写在注释里。`stK` 接受任意记录，只有垃圾构造子规定了长度。一个 `lens.size = 321` 的 inflate 状态在模型中允许下标 320，而 C 只有 320 个单元。静态数组默认为空；任意假设的内容也可能满足一个较弱的定理。审查建议生成形状谓词并由存储操作保持，并建议用与 C 核对过的规范静态数据。内部的形状要求必须由初始化函数确立并一直保持，不能悄悄变成对公开调用者更窄的定义域。

### R6. 分配依赖“新分配”这一点，而不检查它

历史严重程度：中，有条件。审查过的分配器在 `nextBlk` 处写入，不检查它是否未被使用。如果 0 号处有一个存活的字节块且 `nextBlk = 0`，分配就可能覆盖它，并清除它的只读状态。从预期的空堆出发的运行保持了“新分配”这一点，但关于任意堆的定理需要把它明确写出，连同 `nextBlk` 以下各表之间块的唯一性。这里记录的是旧实现；不要把它读成“现在的分配仍会覆盖存活的块”。

### R7. 只读状态没有覆盖每一类对象

历史严重程度：中；对审查过的 zlib 用法为低。字节块和具名静态对象支持只读标记。字块和分配的记录不支持，`freeW` 也不检查它。模型无法表达一般的常量字数组对象。审查过的 zlib 源码不需要这样的对象；将来的翻译或见证不得假设有这种能力。

### R8. 指针相等无条件地区分对象标识

历史严重程度：低到中。派生出来的指针相等使指向不同对象的引用不相等，相邻对象的“末尾之后一个位置”与“起始位置”这两个地址也在其内。C 不一定对每一次这样的比较都给出这个结果。涉及悬空指针的相等比较也仍然可用。审查建议设立一个显式的、带检查的或非确定的相等边界。这些情形是否可达、是否被依赖，需要来自翻译的证据。

### R9. 未初始化的整数在每个单元上只有一个固定的值

历史严重程度：中，属于语义上的选择。`Alloc.lean` 用垃圾值预言给新分配的单元填值，只填一次。因此重复读取得到相同的值；而按 C 的某些解释，未指定的值可以不稳定。依赖这种一致的证明，可能超出模型在 C 上的依据。审查过的 `slide_hash` 和 `longest_match` 的用法没有这样做。旧注释中关于初始化位的说法也不正确；见 R12。

### R10. 整记录复制缺少重叠检查

历史严重程度：中，属于翻译规则的问题。先读取一条记录、再写入，是允许自我复制的；而重叠的 `memcpy` 在 C 中是未定义的。审查过的 `deflateCopy` 和 `inflateCopy` 的各处使用的是不同的记录。将来的复制原语或证明必须既检查对象标识，也检查内嵌记录的重叠。整记录清零也需要审查 C 是否确实把每个字段都清零了；手写的零记录并不自动忠实。

### R11. 较小的原语边界

| 审查当时的观察 | 风险或义务 |
| --- | --- |
| `Ptr.add` 检查的是结果，这使手工伪造的无效指针可以移回范围之内。 | 低；翻译中是否可达尚未确认。带检查的指针操作并不构造那个初始指针。 |
| `Ptr.diff` 通过 `Int64.ofInt` 转换，而不是拒绝溢出。 | 低；例子需要一个有 `2^63` 个元素的数组。 |
| 长度为零的填充或复制也检查只读状态。 | 低；虽然没有写入，仍可能无端出故障。 |
| 通用的 `Ptr.fill` 接受任意的元素值。 | 低；对一个字做非零的 `memset` 需要的是重复的字节，不是这个字节的数值。文档所述的用途是清零。 |
| 悬空指针上的运算和无效的记录转换提早出故障。 | 在审查过的情形中是保守的；C 可能更晚才出错。 |
| 循环的燃料是 `2^64`。 | 这是另一项终止义务，不是 C 的未定义行为规则。 |
| `freeB` 没有分配来源的标签。 | 测试框架的分配可能被当作库的分配释放；所有权的证明必须排除这种误用。 |
| 直接按记录引用做的 `put` 会插入已死的表槽位。 | 存储原语先检查是否存活。直接使用需要仔细审视；它的注释承诺得更多。 |

### R12. 文档夸大或错误地描述了模型

旧文档声称有初始化位、类型标签，以及读未写指针时的故障，而运行时并不提供这些。它们对固定 Huffman 表的位置说法不一：在所选的源码中，`inffixed.h` 由 `inftrees.c` 在 `inflate_fixed` 中包含。生成器用“`not an integer constant expression`”（不是整数常量表达式）作的解释，对冲突的 `COPY` 和对 `GZ_OFF_MAX` 都不对；后者的 `sizeof` 表达式超出了它的求值器的能力。可信基础的文档还错误地说没有差分测试。这些是历史上的不一致，不是对今天的文档的断言。

### R13. 静态数据的生成漏掉了一部分源码依据

历史严重程度：低。`trees.c` 中的 `bl_order` 不在 `Statics` 里。`StaticTreeDesc` 是硬编码的，不是提取出来的，因此源码日后的改动可能被漏掉。审查过的描述符三元组 `(extra_base, elems, max_length)` 是 `(257, 286, 15)`、`(0, 30, 15)` 和 `(0, 19, 7)`。默认的静态值并不确立这些事实。

## 审查记录下来的结构定义对照

审查没有发现 `ZStream`、`GzHeader`、`CtData`、`TreeDesc`、默认构建的 `DeflateState`、`Code`、`InflateState`、`GzFile`、`GzState` 和 `StaticTreeDesc` 中有缺失、次序颠倒或大小不对的字段。它检查了数组长度 573、61、39、16、573、573、320、288 和 1444，以及互不相交的垃圾下标范围。宏和枚举常量的值与所选的默认分支一致，但有上文关于名字和类型的发现。这没有覆盖 `LIT_MEM` 和 `ZLIB_DEBUG`。普通的 `char` 在目标平台上是有符号的；字节指针的表示仍然要求在翻译后的字符读取处做显式的符号扩展。

## 尚未确认的问题 U1–U5

| 编号 | 需要的翻译证据 |
| --- | --- |
| U1 | 有类型对象的对齐、有效类型和字节视图。`uncompr.c` 取 `(Bytef *)&stream.reserved`；CRC 做对齐的宽读取。一个哑字节块可能掩盖别名，而结构定义没有对齐方面的事实。 |

| U4 | 实际的翻译能否像 R11 那样构造出越界的 `Ptr.ref`。 |
| U5 | 除了那两个被清零的状态之外，是否还有哪条分配的记录像 R1 那样在写入指针之前就读取它。 |

## 在审查范围内发现正确的原语行为

审查过的读取和存储操作拒绝 NULL、悬空和越界的访问；存储还拒绝只读的目的地。末尾之后一个位置的指针不可读。字节的 `memcpy` 拒绝重叠，而移动操作在两个重叠方向上都使用原来的源内容。`freeB` 把 NULL 当作空操作接受，并拒绝非零偏移、静态对象、内嵌数组、已释放的块和只读块。块编号从不重用，这支持了审查过的释放后使用规则和重复释放规则。删除父对象使内嵌记录的引用失效。

bind 传播错误，`OkOn` 要求有实际的成功结果，循环规则要求有一个低于燃料的界。块中没有终止符时，`strlenB` 出故障。对源码的这些观察并不确立运行时与 C 完全等价，也不是对某个基线的批准。
