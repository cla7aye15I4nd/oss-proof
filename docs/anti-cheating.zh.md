# 验证策略：问题固定，证明可改

本页说明为什么构建全部通过仍可能毫无价值，验收套件能挡住哪些作弊方式，又挡不住哪些。要点是：证明可以改，但它所回答的问题不能为了让证明通过而改。内核对照类型检查证明；验收套件还要检查这个类型恰好是一个已登记的目标。

构建成功不等于验收。它只让定理成为已检查。只有验收套件在某个具名提交上全部通过，定理才成为已验收（[术语表](glossary.md#status)）。每项结论的层级记在[进度](progress.md#scope)中。[检查指南](checking/README.md)说明每项检查能确立什么；[可信基础](trusted-base.md)列出任何程序都作不了的那些判断。

## 验收套件防得住什么

| 攻击方式 | 防御 |
| --- | --- |
| 证明了一个更弱的命题，却当作目标交出来 | 只有类型与目标完全相同的定理才算证明了目标。多一条前提、名字相近，或者是关于抽象模型的定理，都不算。 |
| 没有依据的假设 | 只允许 `propext`、`Classical.choice` 和 `Quot.sound`。声明审计拒绝导入闭包中的其他公理和被禁止的声明种类。登记表文件缺失、为空，或把同一个名字列了两次，审计就失败。 |
| 内核从未见过的证明项 | 编译后的声明在同一 Lean 内核的全新环境中重放。缓存下来的构建记录不是证书。 |
| 没有登记的目标 | 被审计的闭包中每个独立的 `Goal` 命题都必须登记。`tests/audit/public-api.json` 中的函数清单要与固定版本的头文件、翻译后的入口和手册各节核对。 |
| 必需目标被遗漏，或被悄悄去掉 | 必需目标由 `tests/audit/public-api.json` 算出：目标构建中每个有文档函数的安全目标、所列的安全目标，以及非空性目标。其中任何一个未完成，审计程序就失败。已登记的定理或已证明的目标不得消失，除非 `tests/audit/registry-removals.json` 中有相应的条目和理由。 |
| 不依赖翻译的证明 | 这一项不由验收套件防御。防御手段是证明变异体，它们是额外的证据，只按需运行：故意写错的翻译（例如去掉一处检查）必须通不过检查，而且错误要出在该函数的证明里。审计检查每个已证明的必需目标都有变异体行，但不运行这些行（见[下文](#proof-mutants)）。 |
| 与 C 不一致的翻译 | 差分测试用同样的输入运行真实的 C 和翻译，分别在开启和不开启 sanitizer 的情况下进行。它们是忠实度的证据，不是证明。 |
| `sorry` 和其他被禁止的构造 | 快速关卡在每次推送时拒绝它们。 |

## 它防不住什么

没有锁文件，也没有经过批准的基线。定义、翻译、规格和命题都只由 git 跟踪。如果有人悄悄修改了某个可信的定义、翻译、规格或目标的命题，并在同一个提交里附上用到它的证明，没有任何工具会拒绝。这种修改只在 git 历史和对差异的审查中看得见。

在这种情况下仍然成立的是：

- 目标仍然只能由类型与它完全相同的定理证明，不论修改之后这个类型变成了什么；
- 公理关卡仍然生效；
- 差分测试仍然针对修改后的翻译运行；按需启动变异体运行时，证明变异体也是如此。

这些都发现不了“目标被改得更容易”。依赖某项结论的读者，要把它的目标的命题与 git 中先前的版本作比较。更正命题的规则在 `AGENTS.md` 中：更正需要证据、单独的提交，以及 `tests/verification/regressions/` 下的一个回归。决不为了让证明通过而削弱命题、收窄定义域或修改翻译。

## 什么才算证明

- 登记定理的类型恰好就是目标常量。
- 初始化函数被证明在整个允许的定义域上建立不变量。顶层定理还要加一个具体的见证；它是对全称命题的补充，决不替代全称命题。
- 任何结论都不把库中被调用函数的契约当作未经证明的假设。
- 如果没有任何允许的堆满足某个不变量，它就不能用来支持公开的结论：非空性目标排除了这种情况。

编译器会生成一些标为 `unsafe` 或 `partial` 的辅助声明，例如 `._unsafe_rec`。它们列在 `tests/audit/compiler-helpers.txt` 中，得到豁免。此外任何属于被禁止种类的声明都会被拒绝。

## 证明变异体

证明变异体是额外的证据，不属于验收。完整运行一次需要几个小时，所以它只按需启动（`lean` 工作流的手动触发，并打开它的 `mutants` 选项）。一次运行连同它的提交单独报告，不构成合并、验收或里程碑的关卡。属于验收的审计所检查的，是这些行是否存在。

每个已证明的必需目标都需要变异体行，形式有两种：要么它在 `tests/audit/public-mutants.json` 中有自己的键；要么在 `scripts/verification.py` 的表 `PINNED_EVIDENCE` 中有一项，为没有自己的键的目标（例如序列目标）指明承载证据的变异体列表和带键的目标。

带键目标的每个变异都修改该函数翻译后的函数体，并保持它的签名不变。出现以下情况时审计失败：记录缺失；变异改的是别的函数，或只改了规格；或者它在变异体列表中的那一行带有“可以不被杀死”的豁免标记。在一次变异体运行中，全新内核环境中的重放只把被变异的声明代入原登记证明的依赖闭包。这个证明在变异之前必须通过检查，在变异之后必须失败。只在不相干的定理或更强的定理中失败，不算数。

证明对某处修改敏感，并不说明这处修改改变了行为。等价的改写也可能破坏某个具体的证明项，所以变异应当在某个被允许的输入上改变行为。命令 `verification.py mutants` 运行三组列表：API 边界列表、`public-mutants.json` 的键所引用的每个列表，以及语义安全列表（`scripts/verification.py` 中的 `SAFETY_MUTANT_LISTS`）。安全列表缺失或为空就是错误。各项检查的说明见[变异体指南](checking/proof-mutants.md)。

## 人工审查

契约是否完整、运行时是否表示了选定的 C 的语义、翻译是否与源码相符，都由审查来判断。内核对证明本身的检查替代不了这些。审查的对象是命题、前置条件、运行时、偏离和补丁。审计中遇到的障碍要报告，而不是绕过。
