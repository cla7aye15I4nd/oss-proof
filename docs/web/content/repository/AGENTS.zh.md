# 工作规则

目标：关于上游 zlib `develop` 的一份忠实翻译的 Lean 4 证明，由内核检查。要证明的是默认 x86_64 Linux 构建中每个公开函数的完整安全性（没有未定义行为、没有内存错误、没有泄漏、一定终止）：`inflate` 和 `deflate` 及其调用序列、其余公开函数、gzip 文件接口，以及回调解码器 `inflateBack`。另有一项功能结论也在计划内（所有者 2026-11-15 的决定）：默认 zlib 流的往返，含完备性，见下文。超出安全性所需的其他功能目标不在计划内（所有者 2026-11-11 的决定，为的是早日完成）：计划内的证明所依赖的功能性事实在范围内。已经证明的保留。`zlib.h` 列在`undocumented functions (not part of the zlib API)`（未文档化函数，不属于 zlib API）之下的函数不是必需的。先读 `docs/overview.md`，再读 `docs/spec/safety.md`。证明的讲解放在 `docs/proof/`。当前状态和剩余工作只写在 `docs/progress.md`。

各项安全结论按以下顺序通过验收时，项目即告完成：`inflate` 对每个输入都安全；`deflate` 对每个输入都安全；然后是其余每个公开函数，包括 gzip 文件接口和 `inflateBack`。每项结论都覆盖各自的调用序列，`compress` 和 `uncompress` 的安全性作为组合得出。

安全结论之后是往返，针对默认的 zlib 流（默认级别的 `deflateInit`，`inflateInit`），按以下顺序。先是有条件的形式：一个 `deflate` 调用序列和一个 `inflate` 调用序列都到达 `Z_STREAM_END` 时，不论取什么刷新值、怎样划分片段，`inflate` 写出的字节就是 `deflate` 读入的字节。然后是完备性：输出空间足够且分配成功时，带 `Z_FINISH` 的 `deflate` 消耗全部输入并结束；空间不少于 `deflateBound` 时，一次 `deflate(Z_FINISH)` 调用就结束；空间不少于 `compressBound` 时，`compress` 返回 `Z_OK`；格式所接受的每个流，`inflate` 都能读到 `Z_STREAM_END`。然后是无条件的结论：流的往返，以及 `uncompress(compress(x)) = x`。这些结论的 `sorry` 只能留在骨架分支上。

其他功能正确性（其他级别、策略、窗口大小和封装，预置字典，以及作为往返一方的 gzip 文件接口和 `inflateBack`）、仅关于模型的命题和其他构建配置，都不在计划内。未文档化的函数不是必需的公开目标；已经为它们登记的证明保留。`docs/progress.md` 的“范围”一节列出每一组及其理由。不在计划内的目标，只有计划内的目标需要它时才去做。在保证诚实的前提下尽快工作：流程是为了让结果诚实，不是为了拖慢它。

## 源码

- `zlib/` 是上游子模块。绝不修改它。被验证的源码是 `zlib/` 加上按文件名顺序应用的 `patches/*.patch`。
- 只有已确认且阻碍证明的 zlib 缺陷才允许使用补丁。补丁必须最小，与提交给上游的修复一致，并列在 `patches/README.md` 中。经所有者批准，补丁可以先于向上游的提交落地；这时 `patches/README.md` 把它标为本地、待提交，上游有了修复之后用上游的修复替换它。上游合并了修复、固定版本越过该修复之后，删除这个补丁。
- 翻译与 C 的布局一一对应：`zlib/X.c` 对应 `ZlibF/Zlib/X.c.lean`，`zlib/X.h` 对应 `ZlibF/Zlib/X.h.lean`。每个函数保留它的 C 名字，文档注释以 C 的函数签名开头。
- 规格在 `ZlibF/Spec/` 中。关于 `zlib/X.c` 的证明在 `ZlibF/Proof/X.c.<主题>.lean` 中。公开目标的证明在 `ZlibF/Proof/public-<名字>.lean` 中。
- 不涉及堆的数学放在 `ZlibF/Math/`。运行时（堆、指针、循环、故障）是 `ZlibF/Runtime/*.lean`。

## 翻译

- 逐条语句翻译。不调换顺序，不合并，不化简。有四种规范化写法被采纳（所有者 2026-11-15 的决定），它们不是翻译错误：内部函数的输出参数按值传入，并作为第二个结果返回；对同一位置的两次读取，中间没有写入时，是一次读取；对同一记录的字段的连续赋值，是一次记录更新；有符号运算如果已被同一函数中前面的判断限制在范围之内，就使用普通运算符。除此之外的任何不同都是翻译错误。`docs/design/translation.md` 对每一种各举一例。
- C 能够到达的每个未定义行为都引发 `Fault.ub`。无符号算术回绕。有符号算术带检查。
- 读取未初始化的整数得到一个任意的值，定理必须对每个值成立。新分配内存中的指针在模型里是 NULL，这比 C 弱：证明要说明指针字段在被读之前已经写过（`docs/spec/safety.md` 第 3 节；`docs/trusted-base.md` 第 2 项）。
- 绝不为了让证明容易而改动翻译。与 C 不一致就是翻译错误。改正它，并加一个能抓住它的差分测试。
- 每个证明都依赖运行时。只有确认它与 C 不一致时才改动它。

## 什么算已证明

有两个层级。说话时要说明指的是哪一个。

- **已检查。** 定理在 `dev` 上，并且快速关卡在那个提交上全部通过：所有模块都能构建，没有 `sorry`，没有被禁止的构造。Lean 的内核已经检查了证明。日常工作在这一层级合并。
- **已验收。** 定理还列在 `tests/audit/theorems.txt` 中，并且验收套件在你指明的某个提交上全部通过：公理关卡、目标的精确匹配、自测和差分测试。只有已验收的结果才能报告为最终结果。

证明变异体是额外的证据，不属于验收（所有者 2026-11-15 的决定：完整的变异体运行要几个小时）。变异体运行单独报告，并写明提交。

两个层级都适用的规则：

- 只允许 `propext`、`Classical.choice` 和 `Quot.sound`。绝不使用 `sorry`、`native_decide`、`bv_decide`、`axiom`、`implemented_by`、`extern`、`unsafe`、`partial` 或 `opaque`。不要寻找绕过检查的办法；把障碍报告出来。
- 一个目标只能由类型恰好是该目标的定理来证明。
- 定理把它的前置条件明确写出。比 `zlib.h` 所允许的更窄的前置条件，写在定理的文档注释里，并列在 `docs/deviations.md` 中。绝不悄悄缩小定义域。
- **调用者的区域互不相交。** 调用者提供的、在语义上没有理由重叠的内存区域，如果能让证明更简单，可以假设它们完全不相交：输入、输出、窗口和字典缓冲区，`gz_header` 记录及其 extra、name 和 comment 缓冲区，以及长度单元。前提只是它们的字节范围不重叠：这些区域可以位于同一个堆块中。调用者的字符串（gzip 的 `name` 和 `comment`）假设以 NUL 结尾，它的范围是这个字符串连同它的 NUL。每一条这样的前提都在命题中明确写出，并在 `docs/deviations.md` 中占一行；不需要先有 sanitizer 复现。这条规则不允许按参数的取值来收窄，也不允许丢掉区域并不重叠的、可达的情形。
- **不把被调用函数的契约当作假设。** 被调用函数的规格是关于翻译后的被调用函数的一条定理。表示不变量由初始化函数确立，初始化函数同时说明这个不变量能够成立。只有顶层定理才需要具体的见证。
- 证明卡住时，在四种原因中判断是哪一种，不要预设答案：证明技术、规格有误、翻译错误，或者真实的 zlib 缺陷。怀疑是 zlib 缺陷时，构造一个具体的输入，在 sanitizer 下运行真实的 C，并连同复现一起报告。绝不通过收窄前置条件来掩盖它。
- 差分测试是忠实度的证据，不是证明。报告时要这样说。

## 更正规格、目标或翻译

错误的命题要更正，不要绕开。

- 有证据时才改：一个经过检查的反例，或者有记录的、与 `zlib.h` 或 C 源码的不一致。更正单独放在一个提交里。说明错在哪里，为什么错。
- 把反例作为回归保存在 `tests/verification/regressions/` 下。
- 绝不为了让证明通过而削弱命题、收窄定义域或改动翻译。加强一个偏弱的目标是允许的，也是应当的。
- 翻译与 C 不一致就是错误。改正它，并加一个能抓住它的差分测试。
- 对 `ZlibF/Runtime/` 的改动单独放在一个提交里，写明原因和它影响到的证明。

## 证明工作流程

每项核心结论（`inflate`、`deflate`）有一位负责人。负责人按以下顺序工作。

1. **先检验命题。** 开始一个长证明之前，拿目标同现实对照。用可执行的格式规格对照真实的 C，在许多输入上运行。在小的具体例子上检查目标的每个子句。在这里发现命题有错，代价是几分钟；在证明过程中才发现，代价是几天。按上一节的办法更正它。
2. **自顶向下搭骨架。** 在分支 `skeleton/<结论>` 上，用一组具名引理的命题写出目标的证明，引理本身的证明先空着。`sorry` 只允许出现在骨架分支上，别处都不允许。骨架必须通过类型检查。它就是剩余工作的列表。
3. **公布这份列表。** 把还空着的引理抄到 `docs/progress.md` 的`Core proof skeletons`（核心证明骨架）一节：名字、一句话的含义、状态（未完成、已检查）、以小时计的估计。让它保持最新。
4. **在 `dev` 上补完引理。** 一次证明一条引理，并推送到 `dev`。现有的证明如果恰好适用于引理现在的命题，就复用。骨架不需要的东西不要证明。
5. **把大的定义藏在接口后面。** 一个表示不变量配有一小组接口引理。其他模块使用这些引理，不展开定义。这样，改动不变量时只需重建它的接口，而不是几百个模块。
6. **删掉骨架用不到的东西。** 绑定在某个固定参数或默认配置上、无法为一般引理所用的证明要删除，除非有已登记的定理需要它。
7. **两条引理之间不要停。** 在到达里程碑时、更正命题时，或者在一条引理上两小时没有进展之后报告。报告要写明什么已检查、哪个提交，以及剩余工作的估计。

各位负责人在不同的文件上并行工作。共用构建主机上的重型构建一次只运行一个：等另一位负责人的构建结束，再开始你的。

## 检查

**快速关卡，每次推送和每个拉取请求都运行**（`build`、`no-sorry`）：所有模块都能构建，没有被禁止的构造，补丁能应用到固定的 `zlib/` 上，没有 `sorry`。这是合并的唯一关卡。

**验收套件，每晚在 `main` 上运行，也可按需运行**（`audit`、`difftest`）：公理关卡、目标的精确匹配、自测，以及开启和不开启 sanitizer 的差分测试。按需运行时，使用 `lean` 工作流的手动触发。夜间运行没有全部通过时，要先修好它，再做新的验收工作；但它不阻塞证明工作。

**证明变异体，只按需运行**：手动触发时的 `mutants` 选项。变异后的翻译（去掉一处检查、差一错误）必须无法通过检查，并且错误出在该函数的证明里。它不是合并、验收或里程碑的条件。

没有锁文件。定义、规格和定理的命题只由 git 跟踪：git 的历史就是“什么变了、为什么变”的记录。剩下的保护就是审计本身：只允许规定的公理，并且一个目标只能由类型恰好是它的定理来证明。

属于验收的工作在里程碑处成批完成，不是每次改动都做：

- 把定理登记到 `tests/audit/theorems.txt`；
- 为每个新证明的公开函数准备证明变异体的行，使以后的变异体运行覆盖它；
- 重新生成进度视图。

里程碑是下列之一：`inflate` 已证明，`deflate` 已证明，一个流序列目标已证明，或者大约二十个新近已检查的目标。没有运行过的检查，绝不报告为通过。

完整构建要用很多内存。`ZlibF/Proof/crc32.c.lean` 和 `ZlibF/Proof/inftrees.c.lean` 各需要 8 到 9 GB。构建时至多用四个并行任务，内存上限为 16 GB。如果某个模块需要的比这更多，先弄清原因，再考虑提高任何上限。

## 发现

已确认的 zlib 问题记录在 `README.md` 中：给出简短的描述，链接到 `docs/findings/` 下的复现，并写明置信度和范围。未确认的报告留在 `docs/progress.md` 中。每个新的 sanitizer 复现都放在 `tests/regression/<名字>/` 下，带有 `run.sh` 和 `report.txt`，并在 `docs/sanitizer-reports.md` 中占一行。

## 文档

- 文件名用小写字母，以连字符连接：`method.md`。`README.md` 和 `AGENTS.md` 保留约定俗成的名字。
- 句子要短。写明什么已证明、什么是假设、什么未完成。
- 对 C 的解读如果还须由证明确认，中文页面标记为 **尚未由证明确认**（英文页面的标记是 `**to confirm**`）。
- 结构和顺序用图（mermaid）表示。列表不要画成图。
- 不要把机器名、地址、用户名、本地路径或工具名写进仓库。

## 协作

- 工作落在集成分支 `dev` 上。提交要小而自成一体，直接推送到那里；或者在快速关卡全部通过之后，立即把拉取请求合并进 `dev`。不需要审查。保持 `dev` 能够构建：如果某次推送让快速关卡不通过，先修好它，再做别的事。
- 每到一个里程碑，在验收套件于该提交上全部通过之后，`main` 接收 `dev`。
- 并行的工作使用不同的 C 文件或函数。两位工作者绝不编辑同一个文件。
- 证明全称的目标。不要为某个固定参数或默认配置添加证明，除非它是全称证明的一条引理。
- 提交信息描述所作的改动，不带任何工具的署名行。
- 报告什么已检查、什么已验收、什么未完成。指明提交。

[docs/anti-cheating.md](docs/anti-cheating.md) 说明为什么构建全部通过仍可能毫无价值，以及验收套件防范什么。
